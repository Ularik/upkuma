# Техническая спецификация: система мониторинга сайтов (Uptime Kuma + Telegram Status Bot)

> Документ описывает состав, архитектуру, модификации, конфигурацию, API и порядок эксплуатации/переноса системы.
> Секреты (токены, ключи) в этом документе **намеренно не приводятся** — указаны только места их хранения.

---

## 1. Назначение

Система выполняет периодическую проверку доступности сайтов (HTTP-мониторы) и уведомляет группу Telegram «Мониторинг сайтов»:

- автоматически — при смене состояния монитора UP ↔ DOWN (встроенные Telegram-уведомления Uptime Kuma);
- по запросу — командой `/status` в группе: бот запускает внеплановую (принудительную) проверку всех активных мониторов и присылает сводку.

## 4. Архитектура

```
                ┌──────────────────────────────┐
                │   Telegram (api.telegram.org)│
                └──────▲─────────────▲─────────┘
       sendMessage     │             │  getUpdates (long polling) / sendMessage
   (уведомления UP/DOWN)│             │
┌──────────────────────┴──┐     ┌────┴─────────────────────┐
│ Uptime Kuma 2.5.3        │     │ telegram-status-bot      │
│ node server/server.js    │◄────│ node bot.js              │
│ :3001 (HTTP + Socket.IO) │ HTTP│                          │
│                          │     │ POST /api/monitors/      │
│  SQLite: data/kuma.db    │     │      force-check         │
│                          │     │ GET  /metrics            │
└──────────┬───────────────┘     └──────────────────────────┘
           │ HTTP-проверки (каждые 60 мин)
           ▼
     Отслеживаемые сайты (45 мониторов)
```

Оба процесса работают на одной машине; бот обращается к Kuma по `http://localhost:3001`. Процессы управляются PM2 (`autorestart: true`).

| Процесс PM2 | Скрипт | CWD | Аргументы Node | Переменные окружения |
|---|---|---|---|---|
| `uptime-kuma` | `server/server.js` | `uptime-kuma\` | `--use-system-ca` | — |
| `telegram-status-bot` | `bot.js` | `telegram-status-bot\` | — | `DEBUG=node-telegram-bot-api:*` |

`--use-system-ca` заставляет Node.js доверять системному хранилищу сертификатов (важно для HTTPS-проверок сайтов с корпоративными/локальными CA).

## 5. Данные и конфигурация Uptime Kuma

### 5.1 База данных

`data/db-config.json`:

```json
{ "type": "sqlite", "port": 3306, "hostname": "", "username": "", "password": "", "dbName": "kuma", "ssl": false, "ca": "" }
```

Используется встроенная SQLite (`data/kuma.db`, WAL-режим). Файл `uptime-kuma/db/kuma.db` — шаблон/артефакт исходников, рабочая база — `data/kuma.db`.

### 5.2 Мониторы (состояние БД на момент документирования)

| Тип | Интервал | Интервал повтора | Повторов до DOWN | Активные | На паузе |
|---|---|---|---|---|---|
| `http` | 3600 с (60 мин) | 60 с | 2 | 43 | 2 |

Всего мониторов: **45** (в README.txt указано 44 — при проверке после переноса сверять с фактическим содержимым БД).

### 5.3 Уведомления

| ID | Название | Тип | По умолчанию | Шаблон сообщения |
|---|---|---|---|---|
| 1 | Telegram - uptime Kuma | telegram | да | `{{ name }} — {{ status }}` |
| 2 | Telegram - группа | telegram | да | `{{ name}} - {{status}}` (с ведущим символом табуляции) |

Оба уведомления привязаны ко всем 45 мониторам (90 записей `monitor_notification`). Токен бота и chat ID хранятся в поле `notification.config` (JSON) в БД.

> Два активных Telegram-уведомления на каждом мониторе означают, что при смене статуса уходит два сообщения (если они указывают на разные чаты — это ожидаемо; если на один и тот же — дублирование).

### 5.4 Ключевые настройки (`setting`)

| Ключ | Значение | Смысл |
|---|---|---|
| `apiKeysEnabled` | `true` | API (`/metrics`, force-check) авторизуется API-ключом, а не логином/паролем |
| `keepDataPeriodDays` | `365` | Хранение истории heartbeat — 1 год |
| `disableAuth` | не задан (auth включена) | Обязательно для работы force-check |

Пользователей в системе: 1. API-ключей: 1 — «Telegram Status Bot» (активен, без срока действия).

## 6. Модификации Uptime Kuma

Модифицированы два файла. **При обновлении/переустановке их нельзя заменять стандартными версиями релиза.**
Оригиналы до изменений сохранены как `server/model/monitor.js.bak` и `server/model/monitor.js.before-manual-check.bak`.

### 6.1 `server/model/monitor.js` — принудительная проверка монитора

Цель: позволить выполнить внеплановую проверку монитора, не ломая штатный цикл по таймеру и не допуская параллельных проверок одного монитора.

Изменения в `Monitor.start()`:

1. Добавлены переменные состояния замыкания:
   - `beatPromise` — промис текущей выполняющейся проверки (или `null`);
   - `pendingAutomaticBeat` — флаг «плановая проверка пришлась на время выполнения другой».
2. `beat()` получил параметр `scheduleNext = true`. Следующий `setTimeout` планируется только если `scheduleNext && !this.isStop`. Принудительная проверка вызывается с `false` и **не сдвигает** штатное расписание.
3. Новая функция `runBeat(scheduleNext)` — сериализация проверок:
   - если проверка уже идёт и вызов плановый → выставляется `pendingAutomaticBeat`, вызов завершается;
   - если проверка уже идёт и вызов принудительный → ждёт окончания текущей и затем выполняет **ещё одну** принудительную (чтобы результат был свежим);
   - после завершения, если был отложен плановый тик и монитор не остановлен → запускается `safeBeat()`.
4. `safeBeat()` теперь вызывает `runBeat(true)`; логика перезапуска при исключении сохранена.
5. Публичный метод экземпляра `this.forceCheck()`:
   - возвращает `false` для мониторов типа `push` и остановленных мониторов;
   - иначе выполняет `runBeat(false)` и возвращает `true`.

Результат принудительной проверки обрабатывается так же, как плановой: пишется heartbeat, пересчитывается uptime, при смене статуса отправляются уведомления.

### 6.2 `server/server.js` — эндпоинт `POST /api/monitors/force-check`

Зарегистрирован рядом с `/metrics`, защищён тем же middleware `apiAuth`.

Алгоритм:

1. Если `disableAuth = true` → `403 {"ok":false,"error":"Authentication must be enabled"}`.
2. Выбор мониторов:
   - `apiKeysEnabled = true` (текущий режим) → все мониторы с `active = 1` (ключ уже проверен `apiAuth`);
   - иначе → повторная проверка Basic Auth логин/пароль, при неуспехе `401`; выбираются активные мониторы этого пользователя.
3. Мониторы проверяются **последовательно**. Для каждого статус результата:
   - `NOT_RUNNING` — монитора нет в `server.monitorList`;
   - `PUSH_SKIPPED` — тип `push`;
   - `CHECKED` — `forceCheck()` выполнен;
   - `ERROR` — исключение (пишется в лог).
4. Ответ `200`:
   ```json
   { "ok": true, "total": 43, "results": [ { "id": 1, "name": "…", "status": "CHECKED" } ] }
   ```
5. Необработанная ошибка → `500 {"ok":false,"error":"Internal server error"}`.

## 7. API, используемое ботом

Авторизация обоих запросов — HTTP Basic с пустым логином и API-ключом в качестве пароля:
`Authorization: Basic base64(":" + KUMA_API_KEY)`.

| Метод | Путь | Назначение | Таймаут в боте |
|---|---|---|---|
| `POST` | `/api/monitors/force-check` | Принудительная проверка всех активных мониторов | 300 с |
| `GET` | `/metrics` | Prometheus-метрики, из которых берётся `monitor_status` | 10 с |

Ограничение: `apiRateLimiter` Uptime Kuma — 60 запросов API в минуту; одна команда `/status` расходует 2.

Значения `monitor_status`: `1` — UP, `0` — DOWN, `2` — PENDING, `3` — MAINTENANCE. Бот отображает всё, кроме 0/1, как UNKNOWN.

## 8. Telegram Status Bot (`telegram-status-bot/bot.js`)

### 8.1 Конфигурация (переменные окружения)

Бот при старте читает файл `telegram-status-bot/.env` (через встроенный `process.loadEnvFile`, Node ≥ 20.12 / 21.7; внешних зависимостей нет). Переменные, уже заданные в окружении процесса (PM2, systemd), имеют приоритет над `.env`. Если файла нет — используются только переменные окружения.

| Переменная | Обязательна | Назначение |
|---|---|---|
| `TELEGRAM_TOKEN` | да | Токен Telegram-бота |
| `ALLOWED_CHAT_IDS` | да | Разрешённые chat ID через запятую (группа «Мониторинг сайтов») |
| `KUMA_URL` | нет | Адрес Uptime Kuma, по умолчанию `http://localhost:3001` (завершающий `/` отбрасывается) |
| `KUMA_API_KEY` | да | API-ключ Uptime Kuma («Telegram Status Bot») |

При отсутствии обязательной переменной бот пишет `Не задана переменная окружения <NAME>` и завершается с кодом 1.
Шаблон — `.env.example`; `.env` исключён через `.gitignore`.

### 8.2 Работа

- Реализация на нативном `fetch` (Node ≥ 18), без внешних библиотек.
- Long polling `getUpdates` (`timeout: 30`, `allowed_updates: ["message"]`, HTTP-таймаут 40 с); `offset` хранится в памяти.
- Каждое текстовое сообщение логируется (`Получено: <текст> от Chat ID <id>`).
- Сообщения из чатов вне `ALLOWED_CHAT_IDS` молча игнорируются.
- Команда распознаётся только при точном совпадении текста `/status` (вариант `/status@BotName` не обрабатывается).
- При ошибке Telegram API — пауза 5 с и повтор цикла.

### 8.3 Обработка `/status`

1. `POST /api/monitors/force-check`; если HTTP не 2xx или `ok !== true` → ошибка.
2. `GET /metrics`, разбор строк `monitor_status{…monitor_name="…"…} <value>` (с раскодированием `\"` и `\\`).
3. Отправка сообщения:
   ```
   📊 Статус сайтов

   🟢 <name> — UP
   🔴 <name> — DOWN
   🟡 <name> — UNKNOWN

   Всего: N
   UP: X
   DOWN: Y
   UNKNOWN: Z   (только если Z > 0)
   ```
   Если мониторов нет — «Мониторы не найдены.»
4. При любой ошибке — сообщение «❌ Не удалось получить статус Uptime Kuma.», стек — в консоль.

Время ответа на `/status` определяется суммой времени проверки всех активных мониторов (последовательно); при большом числе медленных сайтов возможен выход за 300-секундный таймаут.

## 9. Развёртывание

### 9.1 Требования

- Node.js 20.4+ (рекомендуется та же мажорная версия, что на исходной системе — 24.x), npm, PM2 или systemd.
- Исходящий доступ: TCP/443 к `api.telegram.org` и к отслеживаемым сайтам.
- Входящий доступ к порту 3001 — только из доверенной сети/через обратный прокси с TLS.

### 9.2 Uptime Kuma

```bash
cd /opt/uptime/uptime-kuma
npm ci --omit=dev          # зависимости по package-lock.json
# dist/ (собранный фронтенд) уже присутствует; иначе: npm run build
# Убедиться, что server/server.js и server/model/monitor.js — модифицированные (сверить с ../server.js и ../monitor.js)
DATA_DIR=/opt/uptime/data/ node --use-system-ca server/server.js
```

Каталог данных по умолчанию — `./data/` относительно CWD; при иной раскладке задать `DATA_DIR`. Пользователь сервиса должен иметь права записи на `data/` (SQLite создаёт `-wal`/`-shm`).

### 9.3 Telegram-бот

```bash
cd /opt/uptime/telegram-status-bot
npm ci
cp .env.example .env      # если .env не перенесён — заполнить значения
chmod 600 .env
node bot.js
```

### 9.4 Автозапуск (PM2)

```bash
pm2 start server/server.js --name uptime-kuma --cwd /opt/uptime/uptime-kuma --node-args="--use-system-ca"
pm2 start bot.js --name telegram-status-bot --cwd /opt/uptime/telegram-status-bot
pm2 save && pm2 startup
```

`pm2-processes.json` — только справка (Windows-пути `C:\UptimeKuma\…`), для импорта в Linux не предназначен.

### 9.5 Альтернатива: Docker Compose (рекомендуется)

Вся система запускается одной командой из корня проекта:

```bash
docker compose up -d --build     # сборка и запуск
docker compose logs -f           # логи обоих сервисов
docker compose down              # остановка
```

| Сервис | Образ | Сборка | Особенности |
|---|---|---|---|
| `uptime-kuma` | `uptime-kuma-custom:2.5.3` | `docker/kuma.Dockerfile`, контекст `./uptime-kuma` | `FROM louislam/uptime-kuma:2.5.3` + `COPY` модифицированных `server/server.js` и `server/model/monitor.js`; том `./data:/app/data`; порт `${KUMA_PORT:-3001}:3001`; `NODE_OPTIONS=--use-system-ca`; встроенный healthcheck образа |
| `telegram-status-bot` | `telegram-status-bot:1.0.0` | `telegram-status-bot/Dockerfile` (`node:24-alpine`, `npm ci --omit=dev`, пользователь `node`) | `env_file: ./telegram-status-bot/.env`; `KUMA_URL` переопределён на `http://uptime-kuma:3001` (имя сервиса в сети compose) |

Оба сервиса — `restart: unless-stopped`, т.е. поднимаются после перезагрузки вместе с Docker (на Ubuntu: `systemctl enable docker`). PM2 при этом не нужен.

Модифицированные файлы накладываются поверх официального образа. Это корректно только для той же версии: исходники `louislam/uptime-kuma:2.5.3` проверены — `monitor.js` совпадает с `monitor.js.bak`, а `server.js` отличается лишь добавленным эндпоинтом. **При обновлении Kuma правки нужно переносить вручную на новую версию и менять тег в `kuma.Dockerfile`.**

Порядок перехода с PM2:

1. `pm2 stop uptime-kuma telegram-status-bot` (две копии одновременно → дубли уведомлений, конфликт `getUpdates`, риск порчи SQLite).
2. Сделать копию `data/`.
3. `docker compose up -d --build`.
4. Пройти чек-лист из п. 12; после успешной проверки — `pm2 delete …` и `pm2 save`.

Замечания:
- Права: процесс Kuma в образе запускается от root, поэтому `data/` доступна на запись без дополнительной настройки. Если перейти на rootless-вариант — `chown -R 1000:1000 data`.
- SQLite в WAL-режиме на bind-mount в Docker Desktop под Windows работает медленнее, чем на нативной ФС Linux; целевая платформа — Ubuntu.
- Чтобы панель была доступна только локально (за обратным прокси), задайте порт как `127.0.0.1:3001:3001`.

### 9.6 Замечание о зависимостях бота

`package.json` объявляет `axios` и `node-telegram-bot-api`, но `bot.js` их не использует (только встроенный `fetch`). Переменная `DEBUG=node-telegram-bot-api:*` в PM2 также ни на что не влияет. Зависимости можно удалить без последствий для работы.

## 10. Безопасность

- **Секреты:** токен бота и API-ключ Kuma хранятся в `telegram-status-bot/.env` (права `600`, не коммитить); токены Telegram-уведомлений лежат в `kuma.db`. Резервную копию хранить в защищённом месте. Ранее секреты были захардкожены в `bot.js`, поэтому могли остаться в старых копиях — при подозрении на утечку перевыпустить токен через @BotFather и API-ключ в Kuma.
- Force-check доступен любому владельцу действующего API-ключа и запускает проверки всех активных мониторов — ключ должен быть только у бота.
- Веб-интерфейс не публиковать в Интернет без TLS и ограничения доступа.
- Не запускать две копии системы с одинаковыми уведомлениями/токеном бота одновременно: дублирование сообщений, конфликт `getUpdates` (Telegram допускает только одного long-polling-клиента на токен).

## 11. Известные проблемы

1. **`KnexTimeoutError: Timeout acquiring a connection. The pool is probably full`** в `data/error.log` (например, 2026-11-10) — пул соединений SQLite исчерпывается при массовых проверках (вероятно, при одновременном срабатывании множества мониторов с часовым интервалом и/или при force-check). Возможные меры: разнести мониторы по времени, увеличить пул/таймаут, перейти на MariaDB.
